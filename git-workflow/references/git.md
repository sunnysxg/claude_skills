# Git 工作流

Git 的目标不是制造提交记录，而是让改动可理解、可验证、可回退，并按项目约定安全地同步。

## 1. 先解析项目规范

项目 `_sxg/project_config.md` 的 `Git workflow` 是 Git Skill 的项目级配置入口。存在时直接
使用，不再搜索其他文档。用户在当前任务中的明确指令可以覆盖本次操作；只有用户确认长期
变更时，才同步更新项目配置。

### 首次解析

`Git workflow` 不存在时，只解析一次：

1. 检查已加载的项目指令，如 `AGENTS.md`、`CLAUDE.md` 及其明确引用的开发文档。
2. 将找到的 Git 规则整理为简短、可执行的字段。
3. 若规则缺失或冲突，只询问会影响当前操作的决定。
4. 把最终结果写入 `_sxg/project_config.md`，以后从这里读取。

没有任何项目规范时，先给一个适合当前项目的建议。不要一次抛出完整 Git 配置表，例如：

> 这个项目还没有 Git 节奏规范。我建议每个可独立回退且验证通过的改动提交一次，阶段完成或
> 交接时再 push。要按这个规则记录并执行吗？

若项目已经指定其他配置登记位置，则使用已有位置。只记录已经确认或能从项目指令明确得出的
字段，保留文件中的其他配置。建议结构：

```markdown
# Project Configuration

## Git workflow

- commit: 每个可独立回退且验证通过的改动提交一次
- push: 阶段完成、交接或跨设备同步前推送
- branch_pr: 沿用仓库现有分支与 PR 流程
- commit_message: 沿用仓库历史风格
- source: AGENTS.md；缺失项由用户确认
- recorded: YYYY-MM-DD
```

`_sxg/project_config.md` 是项目级、跨 agent 的决策登记册，后续可增加运行环境、验证命令、
部署等段落。不要写入密钥、token、机器私有路径或临时状态。若项目要求 `_sxg/` 不入库，
改在项目指定的受管文档中记录，不要强行新增入口。

不要每次 Git 操作都重新搜索项目文档。只有以下情况重新解析：

- 项目配置明确要求刷新。
- 用户说明项目规范已经改变。
- 当前已加载的项目指令与缓存配置明显冲突。
- 配置引用的来源已删除或失效。

## 2. 执行节奏

项目规范可能有不同授权强度：

- 按需：只有用户明确说提交或推送时才执行。
- 宽松：无需逐次询问；在适合的节点自行提交或推送。
- 混合：例如可自行 commit，但 push 仍需用户明确要求。

宽松规范下：

- 一个可独立理解、回退且验证通过的改动形成一个 commit。
- 在高风险改动前、阶段完成后、交接或切换任务前形成清晰检查点。
- 不为每次微小保存制造 checkpoint commit，也不把无关改动混在一起。
- push 通常合并到阶段完成、会话收尾、交接或跨设备同步前；测试失败或工作尚不完整时不推送。

用户对某次操作的直接指令只授权该次操作，除非用户同时把它确认为项目长期规范并更新配置。

## 3. Commit

执行 commit 前：

1. 检查 `git status`、staged/unstaged diff 和最近提交，确认仓库状态与 message 风格。
2. 区分本次改动、用户已有改动和无关文件；只 stage 本次相关的明确路径，不用
   `git add .` 或 `git add -A`。
3. 运行与改动风险相称的验证。失败时修复根因，不靠跳过检查制造成功。
4. 检查待提交文件是否可能包含 secrets、凭据或机器私有配置。

Commit message 优先遵守项目规范；没有格式规范时匹配仓库最近历史。摘要描述改动意图，
正文只在有助于理解原因和影响时添加。不要自动添加 `Co-authored-by`。

提交后再次检查状态并向用户报告 commit 摘要与短 hash。

### Amend 与 hooks

- Hook 或检查失败时修复问题，再创建新 commit。
- 只有用户明确要求 amend，或本次刚创建的未推送 commit 被 hook 自动修改文件时，才考虑 amend。
- 已推送的 commit 不 amend，除非用户明确授权历史重写及其风险。
- 不用 `--no-verify`、`--no-gpg-sign` 绕过检查，除非用户针对该风险明确授权。

## 4. Push、分支与 PR

执行 push 前检查当前分支、upstream、待推送 commits 和工作区状态，并遵守项目的分支/PR
流程。没有 upstream、目标分支不明确或会触发未经约定的发布流程时，先询问。

- 不 force push `main` / `master`。
- 其他分支需要历史重写时，先取得明确授权并优先使用 `--force-with-lease`。
- 不擅自修改 `git config`。
- PR 的创建时机、标题和合并方式以项目规范为准。

## 5. 安全边界

- 不提交 secrets、credentials、私钥或不应共享的机器配置。
- 不覆盖、丢弃或夹带用户已有改动。
- 不执行 `reset --hard`、`clean -fdx`、删分支、重写历史等破坏性操作，除非用户明确批准
  具体目标和风险。
- 多仓库改动分别检查、验证和提交，不混成一个无法独立回退的工作单元。
