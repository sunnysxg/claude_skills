# 交付评论怎么写

直接交付卡交付时的那条评论——她之后确认时唯一能看的东西。人手派会话和自动工作轮都照本文写；
共同讨论卡交回材料不套这个模板（见 discuss.md）。

## 模板

固定头两行，接一栏「用例变化」，然后逐验收项写结果与证据：

```
做了啥：<一句话>
要你干啥：纯归档（已上线）／点完成上线／先按下面步骤验：…
用例变化：新增 N 条 / 删除 M 条 / 改写 K 条；删或改了 <文件:用例名>（为什么：旧行为 ___ 已被
          ___ 取代）；没删的话：本卡改了 ___ 的行为，钉它的旧用例是 ___，为什么还留着。
```

## 用例变化

**改行为的卡必填**——判据：验收标准里有「以前／现在」这种对照，或本卡动了既有用例的期望值。
纯新增功能、纯文档／规则卡写一句「用例变化：无既有行为变化」，不留空。

这一栏要的是**说明删了没、为什么**，不是「必须删」：删不删由这张卡自己判断；但改了行为却一条
旧用例都没动时，必须点名钉旧行为的是哪条、为什么还留着——写不出理由就是该删没删（旧用例钉着
旧行为留在仓里，下次重构先红的就是它们）。

N、M 两个数从候选与基线的 diff 里数，别手数（`<测试目录>` 换成本项目的，todo_hub 是
`dashi-taskboard/test dashi-taskboard/web/src`）：

```bash
BASE=$(git merge-base main HEAD)   # 基线不是 main 时换成卡上登记的基线
git diff "$BASE..HEAD" -- <测试目录> | awk '/^[+][[:space:]]*(it|test)([.][a-z]+)?[[:space:]]*[(]/{a++} /^[-][[:space:]]*(it|test)([.][a-z]+)?[[:space:]]*[(]/{d++} END{print "新增 " a+0 " / 删除 " d+0}'
# 点名删掉／改名的是哪几条（文件头与删除行交替输出）
git diff "$BASE..HEAD" -- <测试目录> | grep -E '^([+][+][+] |[-][[:space:]]*(it|test)([.][a-z]+)?[[:space:]]*[(])'
```

它数的是 `test(` / `it(` 声明行的增删，于是：改了标题的改写被记成一增一删；只改期望值、标题
没动的改写，那行在 diff 里是上下文，命令根本数不到。**K 一律自己在 diff 里数并点名**，别等
命令给。

## `[Sarah]` 项的验收方法

有 `[Sarah]` 项的，逐项给一段能直接照做的验收方法——入口、已准备的初始状态与测试数据、顺序
操作、各关键步骤的预期结果；必要时说明验收环境对应的版本／分支；核心结果藏在 Git、文件或数据库
这类界面外的，给路径／命令并说明对应哪一项。只给 URL、路径、测试命令或「测试通过」不算验收
说明。一次性夹具交付时保持未消费，已经消费就重建或明确说只能验结果。实施中新增过 `[Sarah]`
项的，先单列新增项和原因。

验收入口不发明：不指向本会话起的实例，也不让她跑命令拉起什么。验收入口只给生产实例。常驻 dev
实例（本机 47931 / 公网 `/dev/`）已停用（TODOHUB-493），以下是不再使用的路径，开回来时再看：
开发卡在常驻 dev 实例上验。
