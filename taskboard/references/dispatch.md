# 自动派发的工作会话

prompt 里含「自动派发会话须知」时读本文，它替代 SKILL.md 核心纪律的第 2、6 两条；其余各条照旧。

派发器已经替你认领了卡、开好了树、绑定了会话，所以这类会话的边界比手动会话窄：**只在给定的
工作树里干活**。

## 该做的

- 在给定的工作树里改代码，commit 到当前分支。
- 按 SKILL.md 第 6 条的格式逐项评论交付（含固定头两行）——这是她之后确认时唯一能看的东西。
- 干不下去：评论原因并挪 `blocked`。

## 不该做的

- **不再认领**：卡已经绑定，再挪一次只会打乱派发器的记账。
- **不合并、不 push、不挪 `in_review` / `done`**：会话退出后由派发器接管落位——你自己动手会和
  它抢同一棵树。
- **不收树**：树要留到收尾链跑完，由派发器回收。

## 你是一次性进程

最终回复即进程终点：回合一结束，后台任务与本会话起的一切子进程（测试、监视器、dev 实例）
立即被杀，没有「之后再被叫醒」。

- 要等的命令前台等完再继续，不把 commit 或交付押在后台任务的通知上。
- 交付评论不发明验收入口：不指向本会话起的实例，也不让她跑命令拉起什么。验收一律走常驻
  服务（生产实例与常驻 dev 实例）；常驻 dev 通道尚未就绪时，如实写「入口待常驻通道」。

## 会话退出之后（了解即可，都是派发器的事）

按卡的目的地分流：生产卡在干净轮结束后由派发器补一轮收口、直接发布 main 并部署，进「等你
确认」时已在线上；开发卡合入 dev 集成分支等她放行。失败、树脏、超时都进 `blocked` 并保留候选，
不合并。

她点完成后若有收尾指令投回来（开发卡），系统续上**同一个**自动会话：按 SKILL.md 第 7 条完成
知识收口和 ACK——收口落在当初干活的对话里，因为过程信息只存在那里。
