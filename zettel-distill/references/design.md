# zettel-distill 设计说明

写给六个月后回头改这个 skill 的人（多半是 Sarah 自己或她的 agent）：为什么做、每条规则
是拍板还是踩坑、当时否掉了什么。正文（`SKILL.md`）只写「怎么做」，理由都在这里。
起点是看板卡 CLAUDESKILLS-6（Sarah 2026-08-14 提出，2026-08-18 共同讨论后拍板）。

## 为什么做

**缺口**：neat-freak 收尾链把 agent 侧的四个持久化面（文档、规则、记忆、会话归档）都收了，
但没有人侧的一层——这次会话里 Sarah 真正消化了的概念和判断，该进她自己的 Zettelkasten
的，全靠她事后想起来。

**实证**：2026-08-05 一次会话产出了「需要被指向，才需要独立身份」这条元判据（session log
里有一行），到 2026-08-11 才由另一个会话写成 vault 卡 `1-3-2`——延迟 6 天，中间没有任何
机制在推。这正是「机制不靠自律」说的那种靠人记得才能活的环节。

**为什么挂在 neat-freak 之后而不是另设提醒**：库里 `_hermes/todos.md` 有一条「fleeting →
permanent 日提醒（Hermes cron）」，2026-05-12 立下后一直没动；同期 `#bridge` 标签死了、
`#cctodo` 活着（CLAUDESKILLS-4 实测）。规律是：要求人新建一类动作的机制死，挂在已经在
发生的动作上、且有下游消费者的机制活。收尾是每次都会发生的动作，所以挂在这里。

**为什么是「精选」不是「倾倒」**：Sarah 的原话——一股脑进 vault 的不是她的东西。库的
吞吐数据也支持：fleeting 流入 2026 年稳定在每月 23–41 张，而 Luhmann 卡 7–8 月合计只新建
15 张，瓶颈在裁决不在捕获。再往库里倒候选是加重瓶颈；给她几个是/否的决定才是减负。

**库里的谱系**：这个 skill 的蓝图 Sarah 早就写过——fleeting 卡「知识库的新分工——人只捕获和
裁决，AI做整理和推送」（2026-07-13）第 2 条几乎就是候选卡的规格（起草标题、候选链接各附
一句为什么、标重复与矛盾、把「面对一堆杂物」变成「面对几个是/否的决定」），第 4 条说
「和 Claude 的深度对话本来就是天然的捕获入口，把它接进库」。`2201-2 持久化是分层的` 给了
骨架（选对层，然后挂到将来能被再次触发的地方；登记而不处理，收尾时统一决定）。
`2202 即使有neat freak，文档同步仍然是困难的` 里 Sarah 2026-05-20 写了半句「需要给
neat freak 这种」——本 skill 字面上就是那半句的下文。

## 拍板记录（Sarah 2026-08-18）

每条写选中的内容本身，不写当时的选项代号。

**作者归属——按判断归属分。** 用户在会话里说过的话、做过的取舍 = 用户的判断，agent 只建
桩卡（骨架 = 原话 + 证据点）；agent 从证据推出来的机制类结论由 agent 写全卡并按库内规则
打 AI tag。否掉的两个：① 「AI 永不写 permanent」（库里 2026-07-13 那张 fleeting 卡的说法）——
机制类桩卡会堆着没人填，是 `#bridge` 式死法；② 「agent 全写、打 tag」（2026-07-29 起的实际
做法）——会长出一批正确但没体温的卡稀释她的判断。代价：多一条判定规则要维护；库里那张
07-13 卡的第 2 条若提升为 permanent 时需按此改写。

**入选门槛——双门加上限。** 指向门（`1-3-2 需要被指向，才需要独立身份`）+ 层门（`2201-2
持久化是分层的`），每次 ≤3 条，0 条合法。代价是会漏；但按 `1-3-2` 的判据「提升便宜、降级
贵，宁可晚提不早提」，漏比灌便宜。

**挂链位置——session-log 之后，归档末尾留一节。** Sarah 的原话：先把 log 写好，最后一行
留个位置；她回复要记哪些卡再补进去；不回就是不用提卡。所以顺序是 事实与文档对齐 → 看板 →
session-log → zettel-distill，归档文件末尾有 `## Vault 精选` 一节，候选先以 `[候选]` 记入，
拍板后改 `[已写入]` / `[未提]`，从未回复就保持 `[候选]`。第一轮讨论时 agent 推荐过放在
session-log 之前（理由：归档要记到最终状态），Sarah 改成之后——归档不等她拍板，vault
结果作为末尾一节后补，两边都不阻塞。

**写入通道——只经 vault-ops，不设暂存箱。** vault-ops 是本机专属（gitignored，依赖本机到
sera 的 LAN ssh），别的机器只出提案不写。否掉的：`~/_sxg/vault_inbox/` 暂存箱由后续本机
会话冲刷——多一套没有采集器的机械，违反「先选朴素机制」；等 CLAUDESKILLS-8（机器专属
skill 版本控制）或 OBSIDIANPLAY-1（SMB 通道）落地——阻塞在不相干的决策上。这两张卡改的
都是 vault-ops 内部，本 skill 把它当接口调用不受影响。

**名字——zettel-distill，默认由 neat-freak 触发。** 候选过 vault-distill / vault-closeout；
Sarah 定 zettel-distill：落点是 Zettelkasten 而不是整个 vault，动作是蒸馏。进 public 仓、
manifest 目标 cursor + codex：提案生成是纯推理可移植，只有写入那条腿绑机器。

**时间戳卡用标题指代。** Sarah 看到「202607131046」不知道那是哪张卡；规则写进 vault-ops
（提到 fleeting 卡写标题、时间戳作附注），本 skill 的提案格式照此执行。

**首笔动作。** 第一轮曾问要不要以「提升那张 07-13 fleeting 卡为 permanent」作为 skill 的
第一次实跑；Sarah 未回复，按她定的规则（不回 = 不提）不做。它仍是未来某次提案的自然候选。

## 已知不足与将来可能变的地方

- 双门都是判断题，不是机械检查；靠 SKILL.md 的措辞约束 agent。若实跑后发现候选质量差，
  先改门的措辞和示例，不加更多规则。
- 「用户说过的话 = 用户的判断」在长会话里边界会模糊（她说过一半、agent 补全另一半）。
  规则是拿不准就建桩卡；实跑攒了案例再细化。
- 落点核验依赖 vault-ops 可达。多机部署后如果别的机器也要写，改的是 vault-ops 的通道，
  本 skill 不变。
- 与 neat-freak 的完成合同刻意脱钩：vault 提案未拍板不算 `pending`。这是为了不阻塞收尾；
  代价是「候选一直没人拍」不会有任何东西提醒——`[候选]` 行留在归档里，session-search
  能搜到，但没有推送。若将来发现候选大量沉底，再考虑在看板建卡承接，不在这里加提醒。
